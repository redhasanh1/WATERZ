DEEP DIVE — OPS, PLUGINS, AND TRT COMPATIBILITY

Purpose
- Enumerate TensorRT-sensitive ops by module with exact file locations, and prescribe plugin or fallback strategies. Windows-first guidance (.dll) with Linux notes.

Summary Of Sensitive Ops (by file:line)
1) Deformable Convolution (requires plugin)
   - faster-propainter-main/model/propainter.py:67 uses torchvision.ops.deform_conv2d
   - faster-propainter-main/model/recurrent_flow_completion.py:42 uses torchvision.ops.deform_conv2d
   What to do:
   - Preferred plugin: DCNv2 (DeformableConv2d v2) TensorRT plugin. Sources commonly provided by mmcv/mmdeploy or community DCNv2-TensorRT projects.
   - Ship a Windows build (dcnv2_trt_plugin.dll) and place it on PATH; for Linux, .so on LD_LIBRARY_PATH.
   - In ONNX, this op typically does NOT export cleanly; plan Track A (Torch-TensorRT) first. Track B requires replacing calls with a wrapper module backed by the TRT plugin and/or exporting a custom ONNX op with plugin registry.

2) Grid Sample / Flow Warp (requires plugin in ONNX)
   - faster-propainter-main/RAFT/utils/utils.py: bilinear_sampler uses F.grid_sample (line ~23)
   - faster-propainter-main/model/modules/flow_loss_utils.py: F.grid_sample in flow_warp (line ~25)
   What to do:
   - TensorRT OSS provides a GridSampler plugin (via nvinfer_plugin built from OSS). Ensure you are using a TensorRT build that includes this plugin.
   - On Windows, confirm nvinfer_plugin.dll is from the OSS build containing GridSampler. Add its directory to PATH.
   - With Torch-TensorRT, grid_sample can be lowered internally in some versions; validate. If blocked, keep flow warp in Torch (fallback) while the rest is TRT.

3) Unfold/Fold (im2col/col2im)
   - faster-propainter-main/RAFT/raft.py: upsample_flow uses F.unfold (line ~54)
   - faster-propainter-main/model/modules/sparse_transformer.py: SoftSplit uses nn.Unfold; SoftComp uses F.fold
   What to do:
   - TRT does not have native Unfold/Fold ops. Options:
     a) Replace RAFT upsample_flow with a precomputed, depthwise-conv based equivalent (common RAFT TRT trick). OR
     b) Implement a lightweight plugin for im2col/col2im. OR
     c) Keep this subgraph in Torch-TRT fallback.
   - For SparseTransformer (propainter), prefer Track A (Torch-TRT). For strict ONNX, expect plugin work.

4) Attention and Large Linear Blocks
   - faster-propainter-main/model/modules/sparse_transformer.py: linear projections and attention windows
   What to do:
   - TRT supports Linear + MatMul well; keep shapes bounded (windowed) and use FP16. Ensure dynamic shapes are profiled (min/opt/max H/W per ROI set).

5) 3D Convolution
   - faster-propainter-main/model/recurrent_flow_completion.py: P3DBlock Conv3d layers
   What to do:
   - Supported by TRT. Keep channel dims aligned to Tensor Core multiples for best speed (8/16). Use FP16.

6) Correlation/Cost Volume
   - faster-propainter-main/RAFT/corr.py: CorrBlock uses matmul + bilinear_sampler; AlternateCorrBlock uses alt_cuda_corr (PyTorch CUDA extension)
   What to do:
   - Avoid AlternateCorrBlock (no ONNX/engine path). Keep args.alternate_corr=False (default).
   - CorrBlock path exports better (matrix ops + grid_sample plugin). If blocked by grid_sample, keep CorrBlock subgraph in Torch-TRT or add GridSampler plugin.


Recommended Strategy Per Sub-net (Practical)
RAFT/Flow
- Use ptlflow fastflownet backend already wired in RAFT_bi (faster-propainter-main/model/modules/flow_comp_raft.py: RAFT_bi.__init__). It calls ptlflow.get_model("fastflownet", pretrained_ckpt="things").
  - Advantage: typically simpler ONNX graph than RAFT; fewer exotic ops.
  - Export path: load ptlflow fastflownet and export to ONNX, then build TRT FP16 engine as in Section 2 (update shapes to [1,3,H,W] + second frame).
- If staying with RAFT:
  - Keep CorrBlock (no alt_cuda_corr).
  - Provide GridSampler (grid_sample) plugin.
  - Rewrite upsample_flow to remove F.unfold, or keep that small part in Torch fallback.

RFCNet (Recurrent Flow Completion)
- Uses deformable alignment via torchvision.ops.deform_conv2d (recurrent_flow_completion.py:42).
- Options:
  - Track A: Torch-TensorRT compile and run in FP16 (fastest to integrate).
  - Track B: Replace with DCNv2 ONNX-friendly module and wire TensorRT DCNv2 plugin in exporter + engine build.

InpaintGenerator (ProPainter)
- Uses deformable alignment (propainter.py:67), SparseWindowAttention, SoftSplit/SoftComp (unfold/fold), grid_sample (via flow_warp).
- Options:
  - Track A: Torch-TensorRT with FP16; constrain ROI size to a small profile set.
  - Track B: Mixed approach: export most conv/linear blocks to ONNX+TRT, keep deformable + grid_sample + fold/unfold in Torch via segmentation of the model (advanced). Typically not worth initial effort; prefer Torch-TRT.

ADVANCED OPTIMISATION IDEAS — LAYER BY LAYER

Goal: push beyond straightforward TensorRT conversion by altering the model itself for Tensor Core dominance, minimizing memory movement, and enabling future INT4/custom kernel paths.

1) Flow Backbone (flow_comp_raft.py, ptlflow fastflownet)

2) Deformable Alignment Blocks (propainter.py: DeformableAlignment; recurrent_flow_completion.py: SecondOrderDeformableAlignment)
